## Current status

Version 0.2.1 fixes standalone slash-menu styling, adds block-aware ghost text,
and groups continuous typing into word-like undo units. Canonical Document v2
is unchanged. Application dependency updates and integration verification remain
a separate consumer task. Local validation does not publish the package; the
Release workflow stages the verified tarball. A maintainer then approves that
staged version in npm with 2FA before it becomes public.

## Trusted publishing setup

The Release workflow uses npm trusted publishing through GitHub Actions OIDC.
It runs on a GitHub-hosted runner with `id-token: write`, Node 22 and npm
11.21.2. Publishing does not read an npm token secret, and the release job does
not restore dependency caches.

In the npm package settings for `@startupmedia/scriptr-editor`, register a GitHub
Actions trusted publisher with these exact, case-sensitive values:

| Field                | Value                                      |
| -------------------- | ------------------------------------------ |
| Organization or user | `StartUpMediaUK`                           |
| Repository           | `scriptr-editor`                           |
| Workflow filename    | `release.yml`                              |
| Environment          | `npm`                                      |
| Allowed action       | Staged publishing with `npm stage publish` |

The workflow filename excludes `.github/workflows/`. The `npm` environment
matches the publish job. Register this relationship in npm before dispatching
the Release workflow on `main` with `publish=true`. Workflow reruns retain their
original commit; dispatch a new run to use an updated workflow.

The workflow deliberately does not call `npm publish` or approve its own staged
release. After it succeeds, open npm's **Staged Packages** tab, review the staged
package and its release evidence, then select **Approve** and complete 2FA.
Alternatively, an authenticated maintainer with npm 11.15+ may run
`npm stage list @startupmedia/scriptr-editor`, inspect the returned stage with
`npm stage view <stage-id>`, then approve it with `npm stage approve <stage-id>`.
See [npm's staged publishing documentation](https://docs.npmjs.com/staged-publishing/).

See [npm's trusted publishing documentation](https://docs.npmjs.com/trusted-publishers/).
The existing `NPM_TOKEN` GitHub secret is unused by this workflow. Remove or
revoke obsolete credentials through the owning account once OIDC publication
has been verified.

## 0.2.1 compatibility

The optional `PresentationConfiguration.accentColour` CSS colour configures
controls and their portals; defaults require no new configuration. Import
`@startupmedia/scriptr-editor/styles.css` once. Tailwind scanning is unnecessary.
Headings 4–6 now also appear in the slash catalogue. Equivalent controlled echoes
preserve history and selection, while genuine external replacements clear undo
and redo. See [React integration](/docs/react) and
[Styling and presentation](/docs/styling) for the exact behavior.

The 0.2.1 packed Chromium acceptance check runs with
`pnpm exec playwright install chromium` followed by `pnpm package:browser-check`.
It records 40 assertions, screenshots and computed contrast in
`.local/release-evidence/`; the Release workflow uploads this evidence. Native
OS IME behavior is represented by simulated composition events. Physical touch,
live screen readers and other browser engines are not certified by that check.

The package declares ESM exports, React/React DOM 18.3.1 or React 19 peer compatibility, and Node 20.19+ runtime support. Workspace development uses Node 22.14+ and pnpm 11.19.0; CI runs the full gate on Node 22.14 and 24. A declared range is not proof every runtime/peer combination has been exercised locally.

## Verified foundation

- Repository formatting, lint, TypeScript, unit/component tests and production builds.
- Deterministic document migration and serialization, provider contract tests, commands and history coverage.
- Packed-artifact ESM/type resolution, consumer import/SSR checks and dependency license policy.
- Playwright Chromium interaction, responsive, dark theme, emulated touch, reduced motion and forced-color checks performed during development.

Development verification does not certify live screen-reader behavior, physical touch devices, every OS IME or every browser engine. Automated accessibility scans also cannot certify arbitrary user-authored colors and host extensions.

Packed installs enforce strict peer dependencies. The smoke checks import the installed tarball, render the editor and renderer under React Strict Mode on the server, and resolve a local Scripture passage. They do not certify React 18 interactive browser behavior or every version within a peer range. The ordinary package gate repeats React 18/19 packed smoke checks under its invoking Node runtime; optional `--runtime` paths exercise additional installed Node executables without changing the system runtime.

Two unused React-19-only private authoring modules are excluded from the runtime artifact; their dependency remains development-only. Public runtime components and APIs are unchanged.

## Replacement decision

The implementation is a candidate for owner review, not authorization to publish. Live licensed provider verification, physical-device/screen-reader testing and cross-engine certification are not claimed. A release must explicitly accept or resolve those limits and select its version/publication authority.

Release review covers provider/example coverage, framework boundaries, migration guidance, the exercised runtime/peer matrix and unresolved verification limits. Live YouVersion validation requires a licensed host and credentials. The docs and harness should not imply otherwise.

Current emitted-file ceilings are 900,000 bytes of JavaScript and 120,000 bytes of CSS, enforced by `check-budgets.mjs`. These measure package build output, not gzip transfer size or an application's final bundle. Vite's existing large-chunk warning remains a consumer-bundling consideration.

Run `pnpm check` from the repository root before requesting review or preparing a release. It covers formatting, lint, types, tests, builds, budgets, package/packed-artifact validation and licenses. Changesets/version selection and publication require the owner's release decision; neither a green test run nor this guide grants publication authority.
